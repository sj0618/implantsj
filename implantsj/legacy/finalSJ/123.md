# 유연한 작업 구조 설계

## 1. 목적

임플란트 실험을 하나의 거대한 실행기로 묶지 않고, 작은 단위 작업을 명시적으로 조합하는 구조로 설계한다. 데이터 분할, 학습, 임베딩 추출, prototype 생성, 평가, 시각화, 결과 비교를 각각 독립적으로 실행할 수 있어야 한다.

이 구조의 목표는 다음과 같다.

- 모델, 데이터, checkpoint, seed, 거리 함수 중 하나만 바꿔 다시 실행할 수 있다.
- 실패한 단계만 재실행하고 이미 생성한 결과는 그대로 재사용한다.
- 폐쇄망에서도 짧고 명시적인 명령으로 실행할 수 있다.
- 모든 결과가 어떤 입력과 설정에서 생성됐는지 추적할 수 있다.
- 기존 학습·평가 코드를 불필요하게 수정하지 않는다.

## 2. 원칙

### 2.1 한 명령은 한 작업만 수행한다

각 명령은 입력 하나의 조합을 받아 결과 디렉터리 하나를 생성한다.

- `validate-data`: 데이터 매니페스트 하나 검증
- `build-split`: split 하나 생성
- `train`: 모델·학습 설정·seed 하나 학습
- `extract-embeddings`: checkpoint·view·embedding output 하나 추출
- `build-prototype`: embedding·prototype 방식·거리 geometry 하나 생성
- `evaluate-prototype`: query·prototype·distance·candidate space 하나 평가
- `visualize-tsne`: embedding·geometry·seed 하나 시각화
- `compare-results`: 이미 생성된 결과 두 개 비교
- `diagnose-geometry`: embedding geometry 하나 진단
- `linear-probe`: 지정된 train/test embedding으로 probe 하나 평가

명령 내부에서 다른 모델이나 seed를 자동 순회하지 않는다. Cartesian product와 실험 suite도 기본 실행기의 책임으로 두지 않는다.

### 2.2 설정과 실행을 분리한다

반복 사용되는 설정은 매니페스트에 두고, 실행할 때 달라지는 값은 CLI 인자로 전달한다.

| 구분 | 매니페스트 | CLI 인자 |
|---|---|---|
| 데이터 | source, label space, alias | dataset manifest 경로 |
| split | 비율, 정책, seed 기본값 | split manifest, output |
| 학습 | model, objective, optimizer, scheduler | checkpoint, seed, output |
| 임베딩 | model 구조와 output 이름 | checkpoint, view, output |
| 평가 | 결과 파일 형식 | query, prototype, distance, candidate space |

이 구분을 통해 매니페스트 복제를 줄이면서도 실행 조건은 명령 자체에서 확인할 수 있다.

### 2.3 입력과 출력은 파일 계약으로 연결한다

단계 간 연결은 메모리 객체나 숨은 전역 상태가 아니라 파일로 이루어진다.

```text
Dataset manifest
  └─ build-split
      └─ split metadata + view CSV
          └─ train
              └─ checkpoint + training metadata
                  └─ extract-embeddings
                      └─ embeddings + embedding metadata
                          ├─ build-prototype
                          │   └─ prototypes + prototype metadata
                          │       └─ evaluate-prototype
                          │           └─ metrics + predictions
                          ├─ visualize-tsne
                          ├─ diagnose-geometry
                          └─ linear-probe
```

각 단계는 바로 앞 단계의 구현을 알 필요가 없고, 합의된 산출물 형식만 알면 된다.

## 3. 계층 구조

### 3.1 Shell wrapper

`scripts/*.sh`는 사용자가 실행하는 가장 얇은 진입점이다.

책임:

- 저장소 기준 경로 설정
- Python 모듈 호출
- 전달받은 인자를 변경하지 않고 넘김

비책임:

- 실험 조건 자동 생성
- 여러 명령 반복 실행
- 결과 검색 및 암묵적 선택
- Python 비즈니스 로직 복제

### 3.2 CLI 계층

`implantsj.workflow.individual`은 인자를 파싱하고 작업별 handler를 호출한다.

책임:

- 필수 인자 검증
- 사용자 오류를 일정한 exit code로 변환
- 명령과 handler의 일대일 연결
- 성공 시 생성된 결과 경로 출력

### 3.3 작업 계층

각 handler는 독립적인 함수로 유지한다.

```text
parse arguments
→ load and validate manifests
→ resolve input paths
→ reject unsafe output path
→ execute one operation
→ write artifacts and metadata
→ return output path
```

작업 함수는 다른 작업 함수를 연쇄 호출하지 않는다. 공통 계산이 필요하면 하위 도메인 함수로 분리해 재사용한다.

### 3.4 도메인 계층

기존 `implantsj` 모듈을 재사용한다.

- 데이터 구성: `manifests`, `data`
- 모델 로딩: `models`
- 학습: `training`, `losses`
- 평가: `evaluation`
- 시각화: `visualization`
- 결과 계약: `contracts`, `reporting`

workflow 코드는 이 기능들을 연결하지만 동일한 학습·평가 알고리즘을 다시 구현하지 않는다.

## 4. 산출물 계약

모든 작업 결과는 새로운 디렉터리에 저장한다. 기존 디렉터리가 존재하면 덮어쓰지 않고 실패해야 한다.

권장 구조는 다음과 같다.

```text
outputs/
  splits/<split-id>/
  train/<model>-<condition>-seed<seed>/
  embeddings/<model>/<view>-<output>/
  prototypes/<model>/<prototype>-<geometry>/
  evaluations/<experiment-id>/
  visualizations/<experiment-id>/
  comparisons/<comparison-id>/
  diagnostics/<diagnosis-id>/
```

각 결과 디렉터리에는 최소한 다음 정보가 있어야 한다.

- 실행 명령 또는 정규화된 인자
- 입력 파일 절대 경로
- 입력 manifest hash
- split hash
- checkpoint hash
- embedding hash
- seed
- 생성 시각
- 코드 또는 버전 식별자
- 성공 상태와 주요 출력 파일 목록

결과 이름은 사람이 읽기 쉽도록 만들되, 재현성 판단은 이름이 아니라 metadata와 hash를 기준으로 한다.

## 5. 구성 교체와 부분 재실행

### 5.1 모델 교체

모델 구조는 model manifest로 교체한다. 임베딩 추출 명령의 나머지 입력은 유지할 수 있어야 한다.

```bash
bash scripts/extract-embeddings.sh \
  --dataset-manifest manifests/data/implant_v1.yaml \
  --split-dir outputs/splits/seed42 \
  --model-manifest manifests/models/vit_fullft.yaml \
  --checkpoint outputs/train/fullft_seed42/checkpoints/best.pt \
  --view closed_test \
  --embedding-output encoder \
  --output outputs/embeddings/fullft/closed_test
```

### 5.2 데이터 view 교체

동일한 checkpoint에서 `closed_test`, `open_test`, `gt_closed`, `train`을 각각 독립적으로 추출한다. 한 view의 실패가 다른 view 결과를 무효화하지 않는다.

### 5.3 거리 함수 교체

prototype 원본과 평가 distance를 명시적으로 구분한다. cosine과 euclidean 결과는 별도 출력 경로를 사용하며 기존 결과를 덮어쓰지 않는다.

### 5.4 seed 교체

split seed, training seed, support sampling seed, visualization seed를 서로 다른 인자로 취급한다. 하나의 전역 seed가 모든 단계에 암묵적으로 전파되지 않도록 한다.

### 5.5 부분 재실행

checkpoint가 이미 있으면 학습 없이 임베딩부터 시작할 수 있고, embedding이 있으면 prototype이나 시각화만 다시 실행할 수 있다. 비교 단계는 학습 코드를 import하지 않고 기존 평가 결과만 읽는다.

## 6. 실패와 재시작 정책

- 입력 파일이 없으면 작업 시작 전에 실패한다.
- manifest의 알 수 없는 필드는 무시하지 않고 오류로 처리한다.
- label space와 checkpoint class 수가 다르면 추론 전에 실패한다.
- embedding 차원이 prototype과 다르면 평가 전에 실패한다.
- 기존 output 경로는 덮어쓰지 않는다.
- 부분 생성물이 생길 수 있는 작업은 임시 경로에 기록한 뒤 성공 시 최종 경로로 이동한다.
- 실패한 결과를 성공 결과처럼 소비하지 않도록 완료 metadata를 마지막에 기록한다.

재시작은 기존 디렉터리를 수정하는 방식보다 새로운 output 경로를 지정하는 방식을 기본으로 한다. 동일 조건 재실행 여부는 metadata hash 비교로 판단한다.

## 7. 새 작업 추가 규칙

새 기능은 다음 조건을 만족할 때 별도 명령으로 추가한다.

1. 독립적으로 재실행할 가치가 있다.
2. 입력과 출력 파일 계약을 명확히 정의할 수 있다.
3. 기존 명령의 의미를 확장하는 것보다 새 명령이 더 명시적이다.
4. 다른 조건을 자동 순회하지 않고 한 작업만 수행한다.

추가 순서는 다음과 같다.

1. 도메인 함수가 이미 있는지 확인한다.
2. 입력·출력 계약을 정의한다.
3. handler를 작성한다.
4. CLI subcommand와 shell wrapper를 연결한다.
5. 정상 경로, 잘못된 입력, 기존 output 거부를 테스트한다.
6. `WORKFLOW.md`에 실제 실행 예시를 추가한다.

## 8. 하지 않는 것

다음 기능은 기본 workflow에 넣지 않는다.

- 모든 모델과 seed의 자동 조합
- 최신 checkpoint 자동 검색
- 디렉터리 이름으로 조건 추론
- 누락된 결과의 자동 생성
- 기존 output 자동 삭제 또는 덮어쓰기
- 실패한 단계를 숨기고 다음 단계 계속 실행
- 데이터, 학습, 평가를 한 명령으로 묶는 거대 pipeline

반복 실행이 필요하면 외부 shell script, 작업 스케줄러, CI 또는 별도 orchestration 계층에서 개별 명령을 호출한다. 개별 명령은 단순하고 재현 가능하게 유지한다.

## 9. 완료 기준

유연한 작업 구조는 다음 조건을 만족할 때 완료된 것으로 본다.

- 각 단계가 독립 명령으로 실행된다.
- 모델, seed, view, prototype, distance를 개별적으로 교체할 수 있다.
- 단계 사이의 모든 연결이 명시적 파일 경로다.
- 결과가 기존 파일을 덮어쓰지 않는다.
- 결과 metadata만으로 입력과 설정을 추적할 수 있다.
- 실패한 단계만 새로운 output에서 재실행할 수 있다.
- 단일 명령 테스트와 단계 연결 테스트가 모두 통과한다.

## 10. Canonical metric-learning 상태 전이

metric-learning 진단도 기존 구조를 바꾸지 않는다. protocol은 실행 계획이 아니라
각 단일 명령이 입력을 검증하는 불변식 계약이다.

```text
validation evaluation 30개 완료
→ pretest ledger에 validation hash와 미래 test 경로 기록
→ freeze-validation이 commitment 생성
→ 등록된 test cell만 단일 평가
→ 명시적 evaluation/comparison ledger
→ audit-study
```

이 상태 전이로 학습과 validation까지는 test를 읽지 않으며, test 실행 전에
비교 조건과 출력 경로가 고정된다. `freeze-validation`, `audit-study`,
`summarize-uncertainty`는 이미 생성된 명시적 입력만 검증·요약한다. 실험 실행,
디렉터리 검색, seed 반복 기능은 갖지 않는다.

canonical mode는 legacy mode에 대한 opt-in 강화다. `--protocol-manifest`가 있으면
42=27+15 label 계약, 세 seed의 서로 다른 assignment, 독립 GT, sample/content/group
격리, fixed `last.pt`, encoder 출력, full42/all·closed·open 평가와 lineage hash를
강제한다. 인자가 없으면 기존 개별 명령의 계약과 산출물을 그대로 유지한다.
